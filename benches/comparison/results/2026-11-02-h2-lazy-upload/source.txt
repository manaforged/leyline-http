scale-before.txt and scale-after.txt:
SKIP_CORES=1 LO=1000 HI=5000 bash scale.sh
The h2 workload creates one session per connection and one in-flight request per session.
Each endpoint runs count * 5 requests, with count=1000 and count=5000.
The slope is (peak RSS at 5000 - peak RSS at 1000) / 4000.
The /usr/bin/time %M unit is KiB; the original script labels it KB.
This measures peak process RSS growth, not isolated idle-connection storage or a universal per-connection constant.

memory-pairs.txt:
Five repetitions of the same h2 workload, alternating before/after order.
Both binaries use the same origin, request headers, CPU affinity, and connection counts.
Median before: 47.206 KiB; median after: 45.390 KiB.
Median reduction: 1.816 KiB, or 3.847% of the baseline median.
All five paired slopes decreased.

quick.txt: N=10000 REPS=5 KEEP=0 bash quick.sh, before then after for each cell.
quick-reversed.txt: N=30000 REPS=7 KEEP=0 bash quick.sh, after then before for each cell.
PATHS cells: bare=h2/bare/sequential/1 connection; chrome=h2/Chrome156/sequential/1 connection; 8c8=h2/bare/8 in flight/8 connections; 8c256=h2/bare/256 in flight/8 connections.
The binary component of each PATHS entry selects the saved baseline or candidate executable.
Spread is the instruction-count range, not a throughput confidence interval.
The delta columns compare each label with its own prior saved quick.sh result; these new labels have no history, so those columns do not compare before with after.
Sequential throughput changed direction between runs; these samples do not establish a throughput improvement or equivalence.
