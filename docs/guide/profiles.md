# Profile reference

A profile is a TOML file (`crates/leyline/profiles/<family>/<version>.toml`)
describing one browser build: its TLS ClientHello, HTTP/2 `SETTINGS`, HTTP/3
transport parameters, and per-platform identity headers. Bundled profiles are
compiled into `leyline-http` and selected with `SessionBuilder::browser`.

## Latest-build helpers

Each helper resolves to the newest bundled capture for its family (releases can
advance these helpers; pin a concrete `Browser` variant to keep one
fingerprint):

| Helper | Current variant | Default platform | HTTP/3 `Race` |
| --- | --- | --- | --- |
| `Browser::chrome()` / `Browser::default()` | `Chrome158` | Windows | yes |
| `Browser::edge()` | `Edge158` | Windows | yes |
| `Browser::opera()` | `Opera140` | Windows | yes |
| `Browser::brave()` | `Brave158` | Windows | yes |
| `Browser::firefox()` | `Firefox160` | Windows | yes |
| `Browser::safari()` | `Safari27` | macOS | yes |
| `Browser::safari_ios()` | `SafariIOS27` | iOS | yes |
| `Browser::cfnetwork()` | `CfnetworkMacOS26` | macOS | no (`Auto`) |
| `Browser::okhttp()` | `OkHttpAndroid10` | Android | no (`Auto`) |

## Bundled profiles

{{#include bundled-profiles.md}}

`.browser(browser)` claims the first platform its profile covers (Windows →
macOS → Linux → Android → iOS); see
[Platform defaults and call order](sessions.md#platform-defaults-and-call-order).
Chromium-family profiles derive `sec-ch-ua` dynamically from the major version
and brand using Chromium's GREASE brand and ordering rules.

### What the JA4 column means

Every profile records reference JA4 (`[tls.fingerprint]`) and Akamai HTTP/2
(`[h2.fingerprint]`) values verified by the offline `fingerprint_conformance`
test (which gates HTTP/2 on every profile):

- **Gated:** Fixed `extension_permutation`, so offline computed JA4 is exact and gated.
- **Estimated:** BoringSSL permutes extensions per connection (as Chrome and Brave do), so offline JA4 is estimated while live JA4 remains constant (JA4 sorts extensions before hashing).

The live `tls_peet` suite checks every bundled profile against an echo server.

## Provenance and family notes

Each profile's `[meta]` records `capture` and `captured_against` (missing
`captured_against` logs a `tracing` warning on load):

| `capture` | Source |
| --- | --- |
| `browser` | Capture of the shipped browser build |
| `native` | Capture of an OS HTTP stack (`URLSession` / `CFNetwork`) |
| `emulator` | Shipped app on an Android emulator or iOS simulator |
| `headless-shell`, `webview` | Related browser engine build |
| `inferred` | Derived from a neighboring version |
| `self-referential` | Reference values generated by Leyline itself |

### Family highlights

- **Chrome, Edge, Opera, and Brave:** Official builds captured across macOS, Windows, and Linux against `tls.peet.ws` and `quic.browserleaks.com`, plus local HTTP/2 header-kind captures (`Navigate`, `Script`, `Xhr`, `Form`, `FormNavigate`, `SameSite`, `CrossOrigin`). Chrome 150+ adds ML-DSA signature schemes; Chrome 152+ adds Trust Anchor Identifiers (which Edge omits) and GREASE signature algorithms. Brave adds `sec-gpc: 1` and drops `application/signed-exchange`. Over QUIC, Chromium shuffles transport parameters, uses 8/0-byte CIDs, pads Initials to 1250 bytes, and sends `PRIORITY_UPDATE`.
- **Firefox:** Official Mozilla desktop builds (macOS, Windows, Linux) and Android APKs. Fixed TLS extension order, three key shares (`X25519MLKEM768`, `X25519`, `P-256`), per-platform Android HTTP/2 `SETTINGS`, and QUIC `sni_midpoint` CRYPTO splitting with weighted destination CID lengths.
- **Safari and Safari iOS:** Captured via `safaridriver` on macOS VMs, iOS simulators, and physical iPhone hardware (iOS 27). Safari 26+ and iOS 27 add `zstd` to `accept-encoding`; Safari 18+ and iOS 18+ include HTTP/3 (`rotate` transport parameters, 1200-byte Initials); Safari iOS 17 has no `[h3]` table.
- **CFNetwork and OkHttp:** Native macOS/iOS `URLSession` captures (`CfnetworkMacOS26`, `CfnetworkIOS18`, `CfnetworkIOS27`) and OkHttp 4.12 on Android (`OkHttpAndroid10`). Real iOS/macOS apps prefix their own `<App>/<version>` token onto the `CFNetwork` `User-Agent`.
- **Uncaptured fields kept for API completeness:** Chrome Android `[identity.android]` rows beyond Chrome 145 (follow reduced `Android 10; K` UA), macOS/iOS default interface MSS `1460`, and Windows/macOS per-kind header presets (derived from Linux captures).

Raw capture JSON files live in `crates/leyline/profiles/captures/` in the
repository.

## Update cadence

- **Chrome, Edge, Brave, Opera, and Firefox:** New profiles/brand rows follow each stable major release via automated captures across Linux, macOS, and Windows.
- **BoringSSL:** Tracks the revision shipped by the newest bundled Chrome profile.
- **Safari, CFNetwork, and OkHttp:** Recaptured when OS releases or upstream engine versions change.

## Profile data stability

A release can correct data behind a pinned variant such as `Browser::Chrome158`
(noted in `CHANGELOG.md`), and newest-build helpers advance across releases.

- `Session::profile_id()` returns a 16-hex-character hash of the resolved profile data, browser, and platform (`None` for a plain session; hashes the TOML text for custom profiles).
- `Session::load(path)?.build()` checks the saved `profile_id` automatically and returns `Kind::Config` with `err.is_profile_changed() == true` if the data changed.

```rust,no_run
use leyline::{Browser, Platform, Session};

# fn run(saved_id: &str) -> leyline::Result<()> {
let session = Session::builder()
    .browser(Browser::Chrome158).platform(Platform::Windows)
    .build()?;
let changed = session.profile_id().as_deref() != Some(saved_id);
# let _ = changed;
# Ok(())
# }
```

### Freeze the profile data

To make a saved session immune to future bundled-profile edits, export the TOML
with `Session::profile()` and build from `.profile(frozen)`. `Session::save`
then embeds the TOML inside the saved file; see [Accounts](accounts.md#freeze-a-profile).

```rust,no_run
use leyline::{Browser, Platform, Session};

# fn run() -> Result<(), Box<dyn std::error::Error>> {
let session = Session::builder()
    .browser(Browser::Chrome158).platform(Platform::Windows)
    .build()?;
let frozen = session.profile().ok_or("no profile to export")?;
let again = Session::builder()
    .profile(frozen).platform(Platform::Windows)
    .build()?;
assert_eq!(again.profile_id(), session.profile_id());
# Ok(())
# }
```

## Load your own profile

`SessionBuilder::profile(toml)` loads a custom profile TOML using the same
schema and validation as the bundled profiles (useful for a brand-new browser
release not yet bundled):

```rust,no_run
use leyline::{Platform, Session};

# fn main() -> leyline::Result<()> {
let toml = std::fs::read_to_string("profiles/chrome/158.toml").expect("profile file");
let session = Session::builder()
    .profile(&toml).platform(Platform::MacOS)
    .build()?;
# drop(session);
# Ok(())
# }
```

- **Validation:** `build()` fails with `Kind::Config` on invalid TOML, missing `[identity.<platform>]` for the chosen platform, or a `[tls]` `extension_permutation` that disagrees with enabled extensions.
- **`header_style` in `[meta]`:** Valid values are `chromium` (default), `gecko`, `webkit`, `webkit-26`, `webkit-17`, `okhttp`, `cfnetwork`, `cfnetwork-26`, `brave`, and `brave-154`.
- **`key_shares` in `[tls]`:** Lists the exact groups sent in `key_share` (each must appear in `curves`); when omitted, BoringSSL sends the first 1–2 groups.

## Build a profile from a JA3, JA4_r, or Akamai string

`SessionBuilder` can overlay fingerprint strings onto a browser, custom
profile, or bare session without writing TOML:

| Setter | Input format and effect |
| --- | --- |
| `ja3(raw)` | `version,ciphers,extensions,curves,point_formats` — sets cipher list, curve list, and exact extension order (`version` must be `771`, point formats `0`) |
| `ja4_r(raw)` | Raw `JA4_r` or `JA4_ro` string — sets cipher list, extensions, and signature algorithms (hashed JA4 cannot be inverted and fails) |
| `akamai(raw)` | `SETTINGS\|WINDOW_UPDATE\|PRIORITY\|pseudo_order` — sets HTTP/2 `SETTINGS`, connection window, and pseudo-header order (`PRIORITY` must be `0`) |
| `header_order(names)` | Replaces the regular header wire order |

```rust
use leyline::{Browser, Platform, Session};

# fn main() -> leyline::Result<()> {
let ja3 = "771,4865-4866-4867-49195-49199-49196-49200-52393-52392-49171-49172-156-157-47-53,\
           0-23-65281-11-35-16-51-43-45-10-13-5-18-27-17613-51764-65037,4588-29-23-24,0";
let akamai = "1:65536;2:0;4:6291456;6:262144|15663105|0|m,a,s,p";
let session = Session::builder()
    .browser(Browser::Chrome158)
    .ja3(ja3)
    .akamai(akamai)
    .platform(Platform::Windows)
    .audit(true)
    .build()?;
# drop(session);
# Ok(())
# }
```

- Unspecified fields (identity headers, HTTP/3, signature algorithms for JA3, curves for JA4_r) come from the base profile.
- `Response::fingerprint()` reports the resulting `ja3()` and `akamai()`, and `Session::profile()` embeds the overlay in `[[fingerprint]]` so `Session::save`/`load` reproduces it.
- GREASE values enable `grease = true`; data-bearing extensions (`application_settings`, `compress_certificate`, `delegated_credentials`, `record_size_limit`) inherit parameters from the base profile; `padding` (21) must be last. Invalid or unsupported IDs fail `build()` with `Kind::Config`.
